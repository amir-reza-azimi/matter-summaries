How I Use Skills + AI Agents to Run My Life

Channel: Greg Isenberg · Published: 2026-08-19 · Length: 33 min · Watch on YouTube

TL;DR

This conversation makes the strongest case in the batch for treating skills as operational assets rather than personal prompt files. A skill is described as an SOP that teaches an agent how a team performs a specific task. Put those skills in a versioned shared repository, distribute them through a plugin, and the process becomes portable across people and compatible agent tools. The essential benefit is not merely convenience. It is that quality, ownership, rollback, and improvement become manageable at the level of the organization.

Walkthrough

The guest begins with a definition: a skill is a Markdown procedure that captures the way a person wants an agent to handle a recurring task. A proposal, a Notion formatting routine, or an email template becomes more dependable when it carries the relevant structure, constraints, examples, and output standards. This reframes agent use from asking the model to remember a good conversation to giving it an explicit, reusable procedure. The comparison is to a human SOP. The agent can execute the work more consistently when the operating standard lives outside the prompt of the day.

The problem, according to the interview, is that many useful skills remain trapped on one laptop. Teams pass files through Slack, Drive, Dropbox, or an ad hoc shared folder, but those copies drift. Agent tools also typically load instructions from a particular directory, so an external document is not automatically available at runtime. A talented operator can patch around this with symlinks and manual updates. That is not a workable distribution model for a wider team, particularly when the people who benefit most from the skill are not the people who can repair its technical setup.

The proposed answer is a team repository. Skills live in one source-controlled location, organized by function or project, and the repository can be packaged as a plugin for Claude Code, Codex, or another compatible harness. When a skill changes, the update flows to everyone with the plugin installed. Git history creates a record of why the process changed and enables rollback if a revision makes outcomes worse. Putting the repository in the organization's account also changes ownership. The process remains an asset of the company even if the original author leaves.

The interview then gets more concrete about the types of skills worth sharing. Examples include brand voice and content formatting, Notion conventions, and email delivery standards. These are not glamorous model innovations. They are the high-frequency quality constraints that otherwise get restated in every request or lost when work changes hands. The guest's phrase is effectively thin agents and thick skills: keep the harness relatively interchangeable, but make the procedure, source material, and quality bar explicit. That avoids tying the organization's operational knowledge to one product or one individual's prompt history.

Distribution is only one part of the model. The guest also describes a web interface over the repository that maps which skills call or depend on others, recommends a skill for a task, and records usage. That is useful because a large library without discoverability becomes another form of clutter. Usage data can show which skills are genuinely helping people and which have become stale. It also makes maintenance a product problem: improve the high-leverage skills, retire redundant ones, and use feedback from real runs to evolve the system.

The closing theme is self-improvement. When an agent completes a task, the team can capture a correction as a skill improvement rather than treating the correction as a one-off conversation. The review still needs human judgement. A bad outcome might reflect a missing source, a weak instruction, a wrong tool, or an inappropriate task boundary. But a versioned skill repository gives that judgement a durable destination. It turns repeated prompting into a process of compounding operational knowledge.

Standout moments

The key insight is that sharing skills means sharing quality, not just files. The other sharp point is the ownership test: if a valuable instruction disappears when one employee leaves, it was never a robust company process. Versioning and distribution solve that problem more directly than a library of copied prompts.

Why this matters for my work

Amir already runs skills in the vault and uses a mirrored distribution model. This video provides a clean external articulation of why source-of-truth, versioning, plugin packaging, and usage feedback matter, which is valuable for AI-native consulting and the 10x Operator course. So I could use this as the backbone of a module on turning personal agent tricks into maintainable team infrastructure, while retaining a stricter governance layer around skill review and permissions.
