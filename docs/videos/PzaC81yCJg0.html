This Setup Gives Your Team the Same Claude Memory (Steal it)

Channel: Simon Scrapes · Published: 2026-08-03 · Length: 21 min · Watch on YouTube

Simon opens with a poll result that frames the whole video: nearly seventy percent of his community is trying to use Claude across a team, but almost none of them have found a clean way to do it. When he looked at why, the answer was structural. Claude's own memory is tied to a single account. Third-party memory frameworks store what they learn on one machine and are built around a single user. Even MCP connections authenticate as one specific person. Every serious piece of the existing tooling is, in his words, designed to be single player. He even points out that Y Combinator has team infrastructure for agents sitting on its list of requests for startups, which is its own signal that nobody has solved this well yet. So instead of waiting for a purpose-built solution, he tested how far you can get with tools your team probably already uses: Notion, Claude, and one shared memory connector. He is upfront that Notion is swappable for whatever shared drive or file tool you already run, because the underlying logic is what matters.

The whole approach requires a mental shift. Instead of treating context as something each person's Claude individually owns, you treat it as infrastructure the whole team plugs into, complete with permissions, shared tools, and shared memory. The first layer is Notion as the shared context store. Every team member connects Claude to Notion through their own login via MCP, and critically, Claude can only ever read or write what that person already has permission to see inside Notion. You are not building a permissions system, you are inheriting Notion's. Simon demos this directly: a team context page holding brand positioning and a voice-profile markdown file that feeds everyone's content, where he can flip a specific sub-page to invite-only editing while leaving broad view access in place, and that change propagates straight into what Claude can touch. The practical setup is just pasting the Notion URL into your CLAUDE.md or settings with a line like check this URL first for team context.

The second layer is Composio, which solves shared tool access without ever sharing an API key. There are two use cases. For personal accounts, every team member installs one Composio connector inside Claude, signs in with their own login, and then connects their own individual accounts, for example their own Gmail inbox, through that one connector. From there Claude can reach roughly a hundred and fifty two different apps, and no key ever leaves the Composio vault. For shared resources like a brand inbox or company socials, the cleanest path is to give that person a real seat inside the underlying app itself, so permissions pass through Composio when they sign in. For the rarer case of a shared login with no available seats, Composio's MCP gateway can mint a single scoped URL per team with access to just one tool, say only Stripe or only QuickBooks, through one API call. It is more technical and not yet supported in the dashboard, but it avoids ever distributing the actual key. He flags that Composio's pricing is changing soon: the new free plan covers twenty thousand tool calls a month plus three team members, and the paid tier is twenty nine dollars a month for fifty thousand calls with unlimited members.

The third and hardest layer is shared memory itself, handled through supermemory.ai on its nineteen-dollar-a-month pro plan. Simon explains why he went outside Claude's built-in memory: it is per-account, it captures little, and both storage and retrieval are manual. The setup is a Claude plugin synced from a repository that adds seven skills, the key one being project config. The trick is forcing every team member to write into the same named container tag, for example Team OS, rather than letting the tool auto-generate a fresh container per session. Each person runs the same slash command with their own API key pointed at that same container tag, after being invited to the workspace, because signing up independently first creates a private workspace instead. Once that is done, any teammate can pull the reasoning and decisions another teammate stored, inside their own desktop app, without ever seeing raw session logs.

He is honest about where this falls short. First, if someone pulls context from Notion into a session and that gets captured into shared memory, they retain access to that context through memory even after you later revoke it in Notion, because the memory itself was already saved. Second, there is no personal versus shared split in the automatic capture. Everything from every session gets written into the shared bucket by default, so you have to be deliberate about which project folders you run this in and keep client-sensitive work out of team memory entirely. There is also a blunter caveat: the workspace admin can see every team member's personal memories too, which he calls a fair trade for a small, trusted team but a real one worth naming out loud. He says this is exactly why he is still building a purpose-built team operating system rather than treating this stack as the final answer, but as an eighty percent solution assembled from tools most teams already pay for, in a matter of minutes, it is hard to beat.

For my own work this lands directly on the BI team knowledge layer I am already building at join.com: self-serve analytics via agents, a living context library, a compounding knowledge base. This gives me a concrete, testable reference architecture, permissioned shared context in one tool, shared tool access without key sprawl, and a shared memory container, to pilot against or benchmark what I am building internally, and the two failure modes he names, stale permission inheritance and no personal-shared split, are exactly the edge cases worth designing around from day one. It is also strong, ready-made material for the AI-native consulting side: a client-facing story for what a team's first shared Claude setup should actually look like.
