WebMCP: Let AI Agents pay you money

Channel: Greg Isenberg · Published: 2026-08-26 · Length: 26 min · Watch on YouTube

TL;DR

WebMCP is presented as a way to make a browser application legible and actionable to an agent without reducing the product to a headless API. The central claim is that an application can expose a small, conditional list of tools inside its existing interface. An agent can then understand the page, use the relevant tools, and still operate within the signed-in browser session. For Amir, the value is not the speculative revenue claims. It is a concrete design lens for AI-native customer journeys, internal tools, and service offerings.

What sits between APIs and browser automation

The episode draws a map of several ways an agent can interact with software. Raw APIs and conventional MCP servers are powerful but headless: they need an integration designed for a programmatic caller. Computer-use systems work on screenshots and page structure but can be brittle because they must infer the UI each time. In-app agents keep the user in a particular product. WebMCP is positioned between these approaches. The UI remains visible to a person, while an agent receives an explicit menu of actions rather than guessing which pixels or DOM elements matter.

That distinction matters for adoption. Many business applications already have workflows that are valuable but awkward to expose as full APIs. A small set of safe actions can be more realistic: find compatible products, check a property, draft a quote, assemble a configuration, or prepare a support handoff. The agent does not need unrestricted control of every screen. It needs a bounded capability that maps to a real customer or employee goal.

The espresso-store demonstration

The demonstration uses a store that sells espresso equipment. An agent is asked to compare machines, check whether they fit a counter width, identify compatible accessories, add a suitable item to a cart, and apply a coupon. The details are important because they move beyond simple search. The goal has constraints: the buyer has a specific physical space, a usage pattern, and accessories that must work together. The agent can make progress because the product exposes meaningful choices, not because it can imitate a human click by click.

This is a useful test for any agent-facing product surface. Ask whether the application has the facts and actions needed to complete a customer decision. If it does, the next design question is which facts need structured representation and which actions should require confirmation. A recommendation may be safe to automate. A purchase, a contract change, or a customer-facing message should usually pause for explicit approval.

Authentication and conditional tools

The episode highlights browser session login as the permission boundary. When the demonstrator is signed in, more tools appear. When signed out, only a limited public set remains. That is a more usable model than handing an agent a broad API key for every action. The active session already has an identity and product permissions. A well-designed tool layer can expose only what that identity is allowed to do, while keeping the sensitive decision points visible in the normal interface.

This does not eliminate risk. A session-bound agent still needs narrow scopes, clear intent, and a review boundary before irreversible actions. But it suggests a practical implementation sequence: begin with read-only or preparatory tools, log each action, show the evidence used, and require a human confirmation before money, permissions, or external communication changes. That sequence is suitable for internal business tools before it is suitable for a public checkout flow.

Where the pattern could fit first

The suggested early markets are complex commerce, SaaS administration, regulated read-only flows, and internal tools. Complex products are attractive because compatibility and configuration are where customers abandon a journey. SaaS administration is attractive because support teams repeat predictable setup and troubleshooting steps. In a regulated domain, a bounded assistant can explain options or retrieve information without making the final change. Internal tools are the safest place to learn because the users, source systems, and consequences are more controlled.

For commercial departments, the practical insight is to start from a bottleneck rather than a technology label. A marketing operations user may need to inspect campaign configuration, compare target audiences, and prepare a change request. A sales user may need to find account context and construct a compliant proposal. A BI user may need to navigate a dashboard, retrieve a defined metric, and explain the source. Each can be designed as a sequence of tools with named inputs, evidence, output, and an approval point.

The agency and testing ideas

The video proposes an agency that makes ordinary business websites agent-ready, charging a setup fee and a monitoring fee. That exact offer is less important than the associated service: identify journeys that matter, expose useful capabilities, test whether an agent can complete them, and monitor where it stalls. The related agent mystery shopper is a strong operational concept. Instead of only measuring human conversion, run recurring agent scenarios such as buying a product, booking a consultation, filing a claim, or finding a compatible option. The report can show missing descriptions, broken actions, unclear constraints, and paths that an agent cannot finish.

Why this matters for my work

For AI-native consulting, this yields a concrete workshop and diagnostic. I could map a client journey, identify the evidence an agent needs, design a small read-only or preparatory tool set, and write the approval gates before proposing full automation. The practical next step is to choose one commercial workflow, such as qualified quote preparation or marketing-campaign QA, and describe its agent-visible inputs, actions, safety constraints, and completion test. That turns a broad AI strategy conversation into a testable service design exercise.
