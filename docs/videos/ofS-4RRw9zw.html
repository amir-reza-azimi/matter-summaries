What is an AI harness? I build one live in less than 30 minutes

Channel: How I AI · Published: 2026-06-25 · Length: 25 min · Watch on YouTube

The definition offered here is deliberately plain: a harness is code around an AI agent that makes it more effective at a specific job. The code doesn't have to include AI itself, though it usually does; the point of the code is simply to make the agent better at one constrained task. A harness makes sense specifically when the same workflow needs the same setup and the same outcome repeatedly — which is why coding harnesses became the first popular category, but the same logic applies to production-incident response, release prep, support escalation handling, migrations, or even non-technical repeatable processes like research or documentation consolidation.

The use case chosen and built live is debugging Sentry issues for the podcast's own product, ChatPRD — picked specifically because it already involved custom internal tooling, needed both coding and non-coding context, and had clear desired outcomes (a Linear ticket tracked for every fix, a written follow-up doc other engineers could use). The stated reason for building a dedicated harness instead of just using Claude Code or Codex directly: with a general-purpose coding tool you still have to explain the task and your intent from scratch every session, whereas a harness already knows the job, can be deliberately restricted to specific allowed actions (an investigate-only mode that never writes code, for instance), enforces the exact same output format every time without babysitting, and can route different sub-steps to different models rather than using one model for everything.

The architecture demoed: a terminal UI (built with the Ink library, though the video stresses a harness's interface can just as easily be a CLI or a full web app — the interface is not what defines a harness) sits on top of a core built on the Claude Agent SDK, which supplies the same underlying primitives Claude Code itself uses (file access, planning) without any of Claude Code's general-purpose framing. Connected data sources are deliberately opinionated rather than generic MCP access: purpose-built adapters to Sentry, Vercel, Linear, and GitHub, each written to pull specifically the fields useful for bug triage rather than letting the model wander through a general API. The model running the actual work is Sonnet 4.6, chosen deliberately for this specific job rather than defaulting to the most powerful available model.

Live, a real Sentry warning (an edit operation being silently dropped, affecting roughly 150 users hourly) is fed into the harness in investigate-only mode. It gathers evidence, checks it against custom-written adapters, and produces a structured investigation brief: confirmed impact, identified likely root causes with a stated blind spot, a recommendation on whether to open a Linear ticket, and an explicit recommendation on whether the harness itself has enough confidence to attempt an automated fix (in this run, it correctly recommends against fixing without more verification data) — every run's output gets saved to an artifacts folder as a durable record.

Building the harness itself took two parallel sessions — one on Claude Code, one on Codex — with an honest admission that neither one-shot the result: both defaulted to overly rigid, deterministic code and had to be explicitly redirected toward a more agentic design with heavier use of the SDK. Interestingly, Codex produced the better final harness architecture despite that architecture itself being implemented on top of the Claude Agent SDK — a small but useful reminder that the model doing the building and the SDK the result runs on don't have to match.

The five-step method offered for building your own: identify one specific, repeatable workflow; decide what a single run (a "task") needs as input and what output it should produce; write opinionated adapters to the specific data sources involved rather than generic tool access; decide explicitly what the harness is and isn't allowed to do (read-only vs. write access, for instance); and choose which model or model router actually executes the work, before finally building a surface — TUI, CLI, or web app — to interact with it.

This is one of the cleanest available templates for building the kind of narrow, reliable automation amir-azimi's consulting practice and the vault's own automations depend on — the investigate-only mode and opinionated-adapter pattern in particular are directly applicable to any client-facing agent build where reliability and constrained scope matter more than general capability.
