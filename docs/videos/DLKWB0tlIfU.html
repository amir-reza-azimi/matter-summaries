Claude Code Is Quietly Leaving Small Businesses Behind

Channel: Simon Scrapes · Published: 2026-07-05 · Length: 11 min · Watch on YouTube

Every new Claude Code feature ships with messaging implying it's easier and needs no infrastructure — built for non-technical users. But five minutes into actually using managed agents or Claude's routines feature, you're looking at environment variables, MCP credentials, and containers. The video's argument is that this isn't the user's fault: the product itself has been quietly drifting toward a more technical audience over time, and it walks through two concrete examples before laying out a four-step method for staying independent of that drift.

Managed agents are the first example. The launch messaging promised deploying agents ten times faster with no infrastructure needed — exactly what a business owner without technical background would want. But the actual onboarding runs through five steps that escalate quickly: writing a prompt (familiar territory for anyone who's used ChatGPT), then creating an execution environment (a cloud container with networking rules), choosing between restricted and unrestricted network access, setting up a credential vault and connecting MCP servers, and only then starting a session. What was billed as "no infrastructure needed" turns out to mean the infrastructure decisions were just moved behind a nicer interface, not eliminated — comparable to how people end up running with permissions skipped just to save time, without understanding the implications.

The second example is Claude's routines feature for scheduling recurring tasks. Running one locally means your computer has to stay on all day, so the natural move is to run it remotely — but setting that up means selecting a GitHub repository and interacting with GitHub infrastructure just to run something as simple as a weekly review, and the "behavior" configuration step surfaces developer-facing jargon like auto-fixing pull requests. A non-developer business owner doesn't want to think about GitHub pushes, pull requests, or merges — they want version control, consistency, and quality, handled for them, in the same way a tool like n8n handles infrastructure behind a visual builder.

The explanation offered for why this keeps happening is a revenue chart: Anthropic crossed $30 billion in annualized revenue this past April, with roughly 80% coming from enterprise and developer usage, and business adoption has quadrupled over the past year while a key competitor grew only 0.3% in the same period. If 80% of your revenue comes from one segment, you build for that segment — which means small business owners shouldn't expect Anthropic's own tooling to stay tailored to them, and the practical response is building your own portable layer on top of the underlying model rather than depending on features that only work inside Anthropic's ecosystem.

The four-step method: first, write down what you actually need the system to do before touching any specific tool — the video's own list includes injecting the right context automatically, knowing your business/clients/projects, recalling past sessions and decisions, creating repeatable processes with consistent output matching your actual business (not someone else's), running multi-step scheduled workflows, planning that scales with project size, cleanly separating context across clients and team members, keeping outputs in one predictable place, and being accessible from anywhere without depending on your own computer being on. Second, cross off anything all the major providers will likely ship for free within months — remote access and predictable output locations are both cited as things Anthropic, OpenAI, and others are already converging on, so building those yourself is wasted effort. Third, spend your actual time on what's left: for this creator, that's clean context separation between clients and team members, scheduled multi-step workflows tied to repeatable skills, and memory that isn't tied to one vendor's specific file format (CLAUDE.md doesn't automatically become AGENTS.md if you switch to Codex, and a lot of memory-system decisions get baked into that choice). Fourth, identify where the underlying model itself is weak and stack your own layer on top rather than waiting for a fix — memory recall is the example given, addressed by combining ideas from Hermes and other memory architectures into a custom layer that can simply be dropped once Anthropic ships something equivalent natively.

The closing framing is direct: this approach takes longer up front than just using a feature out of the box, but it's what keeps a small business's AI infrastructure future-proof against the fact that Anthropic's own roadmap isn't being built with them as the primary customer.

This is close to a direct articulation of the amir-azimi consulting thesis — helping commercial departments become AI-native without vendor lock-in — and the four-step method (define needs, cross off what's commoditized, build only the bespoke remainder, patch model weaknesses with a portable layer) is usable almost verbatim as a framework slide in a client pitch or the course.
