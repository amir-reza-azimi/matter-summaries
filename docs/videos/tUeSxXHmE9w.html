OpenAI Codex: Build Apps That Work For You 24/7

Channel: Greg Isenberg · Published: 2026-06-04 · Length: 25 min · Watch on YouTube

This video is a live, narrated build using OpenAI's new Codex Sites feature, framed initially as a skeptical question, is this just a worse Replit or Lovable, and answered by actually building something and showing the specific prompts that make it work. The key differentiator argued for Codex Sites over an all-in-one builder like Replit or Lovable: if you're already living in the Codex ecosystem with your context there, Codex Sites lets an agent keep updating your app autonomously afterward, not just generate it once. The tradeoff: Codex Sites is missing built-in auth, databases, payments, email, and analytics compared to an all-in-one builder, and as of this recording you can't yet deploy to your own custom domain, so it's positioned as an internal-tool builder for people comfortable enough to bolt on auth and storage themselves, not a replacement for Replit-style one-prompt full products.

The build itself is a "startup ideas OS," a Kanban-style board (inbox, researching, validating, building, killed) where each card tracks an idea's buyer, pain, proof, next step, and score. It's built in six sequential prompts, each one demonstrated with the actual wording used. The first prompt invokes the sites plugin directly, asks for realistic sample data, and explicitly says "save for review, do not deploy" rather than letting it auto-deploy, which is called out as an important habit since Codex will otherwise try to publish immediately.

The second prompt asks Codex to add persistent storage so ideas survive between visits, but critically asks it to first show the proposed data model and the specific actions the app would need, before writing any code. Codex responds by choosing Cloudflare D1 as the durable store and lays out the record type (an idea card, its content, its current column) and the exact mutations needed: list, add, update, move, score, archive, ensure-seeded, then explicitly waits for approval before touching code. This "ask for the model first" habit is highlighted as especially useful for non-technical builders who wouldn't otherwise know what to ask for.

The third prompt asks for "safe actions", named, bounded mutations (add idea, update idea) rather than arbitrary raw SQL access, so that later automated chats can only call approved operations, not run open-ended database commands. The fourth prompt asks Codex to create a Codex skill, a reusable instruction file, that documents how to read the board, add ideas, move cards, and score them, plus five example commands, so future sessions and even other chats know how to operate this specific app without re-explaining it. The fifth prompt is a "save gate": explicitly checkpoint the current build as a reviewable version without deploying it, confirming build status, storage choice, and access settings, functioning like a manual save point in a video game since Codex doesn't autosave.

The sixth and most important prompt "proves the loop": in a brand-new chat, with no prior context carried over, the instruction simply asks the app (via the skill created earlier) to add a new startup idea to the board. Codex correctly loads the skill, finds the right local API route, and adds the card using only the safe-action layer, no raw SQL, no generic database writes, confirming the whole point of the exercise: a completely fresh conversation can safely operate this app because the skill and safe actions persist independently of any one chat's memory. The video closes by publishing the site live and reiterating the three concepts to internalize: give it memory (a database, or it's just a demo), safe actions (bounded operations an agent can call without a human reviewing raw code each time), and skills (so any future chat, not just the one that built it, knows how to operate the app).

Standout moments

The "prove the loop" test, opening a genuinely fresh chat and confirming it can still operate the app correctly through the skill alone, is a rigorous and rare moment of actually verifying a claimed capability rather than just asserting it works. The explicit "save for review, do not deploy" habit, stated as a specific correction to Codex's default behavior of trying to publish immediately, is a small but consequential operational detail that would otherwise trip up a first-time user.

Why this matters for my work

The memory-plus-safe-actions-plus-skill pattern is a directly portable checklist for building any small internal tool meant to be updated autonomously by future agent sessions, relevant both to BI internal tooling and to any AI-native consulting deliverable built for a client. So I could apply the same three-step checklist (data model first, safe actions before code, skill for future chats) the next time an internal BI tool is scoped with Claude Code rather than Codex, since the underlying pattern is tool-agnostic.
