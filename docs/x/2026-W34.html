Week: 2026-W34 · Window: 2026-08-03 to 2026-08-17 · Sources: 3 posts

TL;DR

This was a thin week for genuinely reusable workflow signal, but the useful material is unusually coherent. Boris Cherny offered both a concrete maintenance-agent operating model and a practical way to inspect the kinds of mistakes coding agents still make. Thariq Shihipar supplied the complementary judgement principle: the scarce skill is not merely generating work, but deciding which problems deserve compute and checking whether an apparently impressive result is actually true.

Claude Code as a maintenance operating system

Cherny described an experiment in which Claude runs daily maintenance routines through a dedicated Slack channel called proj-claude-maintains-apps. The routines span iOS, Android, Desktop, web, CLI, and the Agent SDK. They include a crash fuzzer that opens an app in a simulator, finds crashes, identifies root cause, and fixes them; a duplicate-abstraction unifier; a dead-code remover that first adds logging to test whether suspected dead code is used; and an abstraction-police routine for leaky interfaces. These are bounded, recurring jobs with observable outputs, rather than a single agent asked to improve a whole codebase at once.

Adversarial review is still part of the loop

Cherny's second post is a useful correction to the idea that code generation alone solves software work. He argues that current model errors have shifted away from simple off-by-one mistakes toward system design, user-interface usability, and missing broader context. The proposed countermeasure is adversarial review. It can be as lightweight as asking for a dynamic workflow that adversarially tests every edge case in a simulator, or using a built-in code-review command at a defined intensity.

Compute allocation and thought partnership

Shihipar makes the human role explicit. He names two key skills with AI: compute allocation and thought partnership. Most jobs do not arrive with an objective list of the most important problems. A person still has to decide where expensive model effort belongs. And an apparently strong answer still requires someone who understands the domain deeply enough to judge whether it is real.

Worth a click

Open Cherny's maintenance-agent post for the concrete routine list and its operating cadence. Open the adversarial-review post if you are designing any workflow where an agent's first answer needs a structured attempt to break it. Shihipar's short note is worth keeping as a decision rule: model capability does not remove the need to choose the problem and verify the result.
